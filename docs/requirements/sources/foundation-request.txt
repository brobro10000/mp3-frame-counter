## 3. Establish the review and merge policy

Desired policy for main:

- Changes must go through a pull request.
- At least one eligible, independent approving review is required.
- Dismiss stale approvals when reviewable code changes are pushed.
- Require approval of the most recent reviewable push by someone other than
  the person who pushed it.
- Require all review conversations to be resolved.
- Require the designated CI gate to pass.
- Require the branch to be up to date with main before merging.
- Block force pushes and deletion of main.
- Use squash merging and a linear history.
- Delete merged working branches automatically.
- No owner, administrator, app, or automation bypass entries.
- No automated approval workflows.

Prefer one active branch ruleset targeting main. Use equivalent classic branch
protection only if necessary and only when it preserves these guarantees,
including enforcement for administrators.

Do not turn on a blanket update restriction that also prevents legitimate
PR merges. Do not add a bypass to compensate for an incorrectly configured rule.

Approval identity is a real prerequisite:
- Inspect the authenticated PR-creating identity.
- Do not confuse Git commit author metadata with GitHub PR authorship.
- If the PR is opened under brobro10000, explain that brobro10000 cannot approve it.
- Changing Git author names or email addresses is not a solution.
- Do not assume a bot-authored PR is approvable by me without checking GitHub's
  actual eligibility rules and the most recent pusher.
- Agent review documents or an “APPROVE” string are not human GitHub approval.

If no eligible reviewer is available, keep the approval requirement intact,
complete safe foundation work, and leave the PR blocked pending a reviewer.

Add CODEOWNERS for sensitive repository-control files only with verified owners
and a workable review arrangement. Do not enable an additional code-owner gate
that silently makes the intended reviewer ineligible. Report any deferred
code-owner enforcement separately; the one-review requirement remains mandatory.

If the GitHub plan or credentials cannot enforce the required protections,
report the exact limitation. Do not call the repository protected, make it public,
reduce the approval count, or substitute a local hook.

After that initial commit:
1. Activate PR/review/no-bypass protection before publishing implementation work.
2. Create codex/phase-01-repository-foundation.
3. Add the foundation files and workflows on that branch.
4. Open the foundation PR.
5. Observe the real CI check name and producing GitHub App.
6. Require that exact check and bind it to the observed integration where supported.
7. Read back the effective rules and verify the resulting PR is blocked until its
   requirements are satisfied.

Do not guess check names or GitHub App IDs.
Do not register a nonexistent check and report the setup as verified.
Do not merge anything during this run.

## 6. Implement meaningful CI for this phase

Run CI on pull requests targeting main and on pushes to main.

For now, validate what actually exists:
- Reproducible installation from the lockfile.
- Formatting of tracked configuration and documentation.
- GitHub Actions workflow syntax, including actionlint or an equivalent
  maintained validator.
- Small, useful repository-policy checks where static validation is insufficient.

Avoid application placeholder code, dummy tests, echo-only build jobs, and
“pass with no tests” settings.

Application typechecking, parser tests, endpoint integration tests, and production
build verification belong in a later approved phase. Document them as not yet
implemented rather than manufacturing green results.

Provide one stable terminal required job, preferably named control-plane if that
fits the installed orchestrator's actual contracts.

The terminal gate must:
- Run after all mandatory validation jobs, even when an upstream job fails.
- Explicitly require success from every mandatory dependency.
- Fail on failed, cancelled, unexpectedly skipped, or missing results.
- Never silently pass because a dependency was skipped.
- Have a unique, stable name and no matrix expansion.

Do not path-filter the required workflow so that documentation-only PRs leave it
pending. Avoid continue-on-error, “|| true”, or other failure suppression.

Use the same validation commands locally and in CI.

Security defaults:
- GitHub-hosted runners.
- Read-only GITHUB_TOKEN permissions for PR validation.
- Disable Actions' permission to create and approve PRs.
- No repository-administration credential in CI.
- No deployment secrets in PR jobs.
- Do not use pull_request_target to execute PR-controlled code.
- Pin external Actions to verified full commit SHAs, with version comments.
- Do not interpolate untrusted PR titles or bodies directly into shell commands.
- Disable persisted checkout credentials when unnecessary.
- Set sensible timeouts and cancel superseded PR-validation runs.

Repository settings are applied through the authorized administrative setup,
not automatically by a PR-controlled workflow holding an admin token.

## 7. Establish delivery without inventing a deployable application

For this phase, delivery means a validated, commit-addressed foundation artifact,
NOT a running application or a cloud deployment.

After a push to protected main:
- Run the same required validation.
- Only after success, produce a source/configuration archive from that exact commit.
- Include the commit SHA and an artifact checksum.
- Upload it as a GitHub Actions artifact with a short, documented retention period.
- Exclude .git, credentials, node_modules, caches, and untracked files.

Prefer a job in the same trusted-main workflow, or a small reusable workflow,
rather than a complicated cross-workflow trigger chain.

PR runs must not execute the delivery job.
Do not create public releases, publish packages, push container images, provision
hosting, or add cloud credentials.

Document container packaging and deployment as later work.
Do not describe a source archive as a deployable MP3 service.

Because this run must stop before merging the foundation PR, distinguish
“delivery workflow configured and validated” from “delivery executed on main.”
Do not claim the latter without an observed successful run.
